# Лабораторная работа № 3

## Классификация DNS-трафика и автоматизированный CI-конвейер

Проект реализует бинарную классификацию DNS-трафика с помощью модели машинного обучения и автоматизированные проверки, направленные на повышение надёжности и киберустойчивости системы.

Модель относит DNS-трафик к одному из двух классов:

- `Benign` — легитимный DNS-трафик.
- `Malicious` — потенциально вредоносный DNS-трафик.

Основная цель лабораторной работы — построить CI-конвейер на GitHub Actions, который проверяет код, тесты, зависимости, данные, качество модели и безопасность Docker-контейнера до принятия изменений.

## 2. Запуск CI-конвейера

CI-конвейер реализован с помощью **GitHub Actions**. Его конфигурация находится в файле:

```text
.github/workflows/ci.yml
```

Workflow запускается при следующих событиях:

- `push` — отправка изменений в ветку;
- `pull_request` — создание или обновление Pull Request.

В конфигурации указано ограничение по веткам: workflow запускается для веток, соответствующих шаблону `lab3-*`.

Таким образом, проверки автоматически выполняются для основной лабораторной ветки и специальных веток, предназначенных для демонстрации отказов.

## 3. Архитектура и последовательность Pipeline

Конвейер состоит из последовательных этапов. Зависимости между заданиями задаются параметром `needs`. Если обязательный предыдущий этап завершается ошибкой, зависимые от него задания не запускаются.

Общая последовательность:

```text
Code Quality
     |
     v
   Tests
     |
     v
Dependency Audit
     |
     v
 Data Quality Gate
     |
     v
 Model Quality Gate
     |
     v
  Trivy Config
     |
     v
Docker Build + Smoke Test
     |
     v
   Trivy Image
```

### 3.1. Code Quality — проверка качества кода

Первый этап проверяет Python-код с помощью двух инструментов:

**Ruff**

- проверяет стиль и качество Python-кода;
- обнаруживает распространённые ошибки;
- проверяет каталоги `src` и `tests`.

Команда:

```bash
ruff check src tests
```

**Bandit**

- выполняет статический анализ Python-кода;
- ищет потенциально небезопасные конструкции;
- проверяет исходный код в каталоге `src`.

Команда:

```bash
bandit -r src -ll
```

Если проверка завершается с ошибкой, последующие этапы, зависящие от `code_quality`, не выполняются.

### 3.2. Tests — автоматическое тестирование

На этом этапе устанавливаются зависимости из `requirements-dev.txt` и запускаются тесты с помощью Pytest.

Команда:

```bash
pytest -q --junitxml=reports/junit.xml
```

JUnit XML-отчёт сохраняется как артефакт GitHub Actions. Загрузка отчёта настроена с условием `if: always()`, поэтому шаг загрузки выполняется и при неуспешном тестировании, если файл отчёта был создан.

Автоматические тесты проверяют корректность работы компонентов проекта.

Локальный запуск:

```bash
python -m pytest -q
```

### 3.3. Dependency Audit — аудит зависимостей

Для поиска известных уязвимостей в Python-зависимостях используется **pip-audit**.

Проверяются зависимости, перечисленные в `requirements-dev.txt`.

Команда в CI:

```bash
pip-audit -r requirements-dev.txt \
  --format json \
  --output reports/pip-audit.json
```

Результат сохраняется в JSON-отчёт и загружается как артефакт.

Если аудит обнаруживает уязвимости и завершается с ненулевым кодом возврата, последующие зависимые этапы не запускаются.

### 3.4. Data Quality Gate — проверка качества данных

Проверка реализована в файле:

```text
src/data_quality_gate.py
```

Запуск в CI:

```bash
python src/data_quality_gate.py
```

Этап проверяет CI-набор данных до оценки модели. Это позволяет не допускать к следующим стадиям данные, которые не проходят предусмотренные проектом проверки качества.

При нарушении условий Data Quality Gate завершается ошибкой. Благодаря зависимости `needs` этап оценки модели не запускается.

### 3.5. Model Quality Gate — проверка качества модели

Проверка реализована в файле:

```text
src/model_quality_gate.py
```

Запуск в CI:

```bash
python src/model_quality_gate.py
```

На этом этапе оценивается ONNX-модель на CI-данных. Результат кандидатной модели сопоставляется с baseline и установленным порогом качества.

Проверка не позволяет продолжить конвейер, если модель не удовлетворяет заданным критериям качества.

Результат сохраняется в файл:

```text
metrics/model_gate_result.json
```

Этот файл загружается в GitHub Actions как артефакт `model-quality-report`, если он был сформирован.

### 3.6. Trivy Config — проверка конфигурации

Для анализа конфигурационных файлов проекта используется **Trivy**.

В CI выполняется сканирование типа `config`:

- анализируется репозиторий;
- учитываются находки уровней `HIGH` и `CRITICAL`;
- при обнаружении находок указанных уровней проверка завершается с ошибкой.

Основные параметры проверки:

```yaml
scan-type: config
scan-ref: .
severity: HIGH,CRITICAL
exit-code: "1"
format: json
```

JSON-отчёт сохраняется как артефакт `trivy-config-report`, если он был создан.

### 3.7. Docker Build и Smoke Test

После успешных предыдущих этапов CI собирает Docker-образ приложения:

```bash
docker build -t dns-tunneling-detector:ci .
```

Затем запускается контейнер:

```bash
docker run --rm dns-tunneling-detector:ci
```

Этот запуск является **Smoke Test**: он проверяет, что образ собирается, контейнер стартует и приложение выполняет предусмотренный сценарий запуска.

Дополнительно CI проверяет, что контейнер работает не от имени `root`:

```bash
USER_ID=$(docker run --rm \
  --entrypoint id dns-tunneling-detector:ci -u)

test "$USER_ID" -ne 0
```

В Dockerfile задан отдельный пользователь с UID `10001`.

После успешной сборки Docker-образ сохраняется в архив `image.tar` и загружается как артефакт `docker-image`. Этот артефакт используется следующим этапом сканирования образа.

### 3.8. Trivy Image — сканирование Docker-образа

На последнем этапе Trivy проверяет собранный Docker-образ.

Сканирование настроено на уязвимости уровня `CRITICAL`. Если такие находки обнаруживаются, проверка завершается с ошибкой.

Основные параметры:

```yaml
scan-type: image
severity: CRITICAL
exit-code: "1"
format: json
```

Отчёт загружается как артефакт `trivy-image-report`, если он был сформирован.

## 4. Механизмы безопасности Docker

Контейнеризация приложения описана в `Dockerfile`.

В конфигурации предусмотрены следующие меры:

- используется базовый образ Python с зафиксированным digest;
- устанавливаются зависимости, необходимые приложению;
- удаляются ненужные системные пакеты и временные файлы;
- создаётся отдельный пользователь `appuser` с UID `10001`;
- приложение запускается от имени непривилегированного пользователя.

В конце Dockerfile используется директива:

```dockerfile
USER 10001:10001
```

Это снижает риск выполнения приложения с привилегиями суперпользователя внутри контейнера.

Файл `.dockerignore` исключает ненужные файлы из контекста сборки Docker, например локальные виртуальные окружения, Git-метаданные и временные файлы разработки. Это уменьшает размер контекста сборки и снижает вероятность случайного включения локальных файлов в образ.

## 5. Политики прохождения проверок

В CI используются следующие правила:

| Проверка | Условие успешного прохождения |
|---|---|
| Ruff | Нет ошибок, приводящих к ненулевому коду возврата |
| Bandit | Нет находок, блокирующих проверку при заданном уровне `-ll` |
| Pytest | Все тесты завершились успешно |
| pip-audit | Аудит зависимостей завершился успешно |
| Data Quality Gate | CI-данные прошли проверки качества |
| Model Quality Gate | Модель удовлетворяет требованиям качества и сравнения с baseline |
| Trivy Config | Нет блокирующих находок уровней `HIGH` и `CRITICAL` |
| Docker Build | Docker-образ успешно собран |
| Smoke Test | Контейнер успешно запустился и выполнил smoke test |
| Non-root check | UID пользователя контейнера не равен `0` |
| Trivy Image | Нет блокирующих находок уровня `CRITICAL` |

Проверки Ruff и Bandit отображаются в логах соответствующего задания GitHub Actions. Для этапов, где предусмотрено формирование отчётов, результаты дополнительно сохраняются в артефактах.

## 6. Артефакты GitHub Actions

Workflow сохраняет следующие артефакты:

| Артефакт | Содержимое |
|---|---|
| `pytest-report` | JUnit XML-отчёт Pytest |
| `pip-audit-report` | JSON-отчёт аудита зависимостей |
| `model-quality-report` | JSON-отчёт проверки качества модели |
| `trivy-config-report` | JSON-отчёт проверки конфигурации |
| `docker-image` | Архив собранного Docker-образа |
| `trivy-image-report` | JSON-отчёт сканирования Docker-образа |

Артефакты доступны на странице конкретного запуска workflow в разделе **Artifacts**. Некоторые отчёты могут отсутствовать, если соответствующий инструмент завершился до создания выходного файла.

## 7. Локальный запуск проверок

Для локального выполнения проверок необходимы Python, Docker и установленные инструменты Ruff, Bandit, pip-audit и Trivy.

### 7.1. Создание виртуального окружения

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 7.2. Установка зависимостей

```bash
pip install -r requirements-dev.txt
```

### 7.3. Запуск тестов

```bash
python -m pytest -q
```

### 7.4. Проверка качества кода

```bash
ruff check src tests
bandit -r src -ll
```

### 7.5. Аудит зависимостей

```bash
pip-audit -r requirements-dev.txt
```

### 7.6. Проверка качества данных

```bash
python src/data_quality_gate.py
```

### 7.7. Проверка качества модели

```bash
python src/model_quality_gate.py
```

### 7.8. Сборка Docker-образа

```bash
docker build -t dns-tunneling-detector .
```

### 7.9. Запуск контейнера и Smoke Test

```bash
docker run --rm dns-tunneling-detector
```

### 7.10. Проверка UID контейнера

```bash
docker run --rm --entrypoint id dns-tunneling-detector -u
```

Ожидается ненулевой UID. В текущем Dockerfile задан UID `10001`.

### 7.11. Проверка конфигурации Trivy

```bash
trivy config --severity HIGH,CRITICAL --exit-code 1 .
```

### 7.12. Сканирование Docker-образа Trivy

```bash
trivy image --severity CRITICAL --exit-code 1 dns-tunneling-detector
```

## 8. Демонстрация отказов CI

Для проверки того, что конвейер корректно реагирует на нарушения, используются отдельные демонстрационные ветки:

- `lab3-fail-tests` — демонстрация отказа этапа автоматического тестирования;
- `lab3-fail-model` — демонстрация отказа Model Quality Gate при несоответствии модели требованиям качества;
- `lab3-fail-security` — демонстрация отказа проверки политики безопасности на синтетическом отчёте с находкой уровня `CRITICAL`.

Основная ветка с рабочим CI-конвейером:

```text
lab3-github-actions
```
